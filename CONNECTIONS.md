# Подключения к базам

Администратор открывает «Подключения к базам» в левой панели, заполняет форму и нажимает «Проверить и сохранить». Успешное сохранение ещё не переключает источник: для этого нужно нажать «Выбрать». Вернуться к учебным данным можно кнопкой «Выбрать» у базы ГрГУ. Удаление подключения удаляет только сохранённые реквизиты, а не внешнюю базу и её содержимое.

Поддерживаются существующие файлы SQLite (абсолютный путь **на компьютере, где запущен Flask**), PostgreSQL через psycopg 3 и MySQL 8+ через PyMySQL. Установите зависимости: `python -m pip install -r requirements.txt`. Для серверных БД указываются адрес без URL, порт, база, пользователь и пароль. Произвольные строки подключения и параметры драйвера не принимаются. Подключение служебного файла `app_users.db` запрещено.

Подключения принадлежат создавшему их администратору. Другие администраторы их не видят; гость, аналитик и оператор работают с учебной базой. Выбор действует в текущем сеансе браузера, а не глобально для всех пользователей. При изменении роли доступ проверяется заново. Схема, генерация SQL, история, избранное и меню примеров учитывают активный источник. Старые записи истории и избранного без источника относятся к учебной базе.

Для внешней базы модель получает её фактические таблицы, поля, первичные и внешние ключи и название SQL-диалекта. Содержимое таблиц и реквизиты подключения в промпт не отправляются; университетские шаблоны не используются. Счётчики строк внешних таблиц не вычисляются: вместо полного сканирования показывается «—». Поддерживается текущая схема пользователя (PostgreSQL search_path/default schema); база должна содержать не более 100 таблиц и описание схемы до 20 000 символов.

## Режим чтения

Все внешние подключения, включая SQLite, доступны **только для чтения**, в том числе администратору. Проверяется один SELECT/CTE, запрещаются вложенные изменения, неизвестные функции и SELECT INTO. Дополнительно используются `mode=ro`/`query_only` у SQLite и транзакции READ ONLY у PostgreSQL/MySQL. Для серверного пользователя рекомендуется отдельно выдать только SELECT на нужные таблицы; это также определяет доступ к представлениям и другим схемам.

Изменения учебной базы по-прежнему проходят откат и одноразовое подтверждение. Токен подтверждения привязан к источнику данных и не принимается при переключении на внешнюю базу. Доступ на запись во внешние БД в этом этапе не реализован: в частности, MySQL DDL может неявно фиксировать транзакции, поэтому простой ROLLBACK не даёт необходимой гарантии. См. [документацию MySQL](https://dev.mysql.com/doc/refman/8.4/en/implicit-commit.html).

Для PostgreSQL устанавливаются `statement_timeout` и `lock_timeout`; для MySQL — `MAX_EXECUTION_TIME` для SELECT и сетевые таймауты. Используется существующий SQL_TIMEOUT_SECONDS (по умолчанию 3 секунды). Для SQLite работают прерывание и обработчик прогресса. Результат ограничен 1000 строками; серверные результаты читаются потоково. Ограничение числа строк не ограничивает стоимость вычисления самого SELECT. Интроспекция схемы состоит из нескольких запросов с отдельными таймаутами.

## Хранение и резервное копирование

Реквизиты сохраняются в служебной таблице `external_connections` файла `app_users.db`. Весь набор реквизитов шифруется Fernet; API возвращает только ID, название, тип СУБД и признак чтения. Аудит содержит добавление, выбор и удаление подключения с ID и результатом операции, без пароля, URL и остальных реквизитов. Ошибки драйверов наружу не передаются.

Ключ создаётся при первом сохранении и хранится отдельно в `.connections-key`. Можно задать ключ Fernet через переменную окружения `CONNECTIONS_KEY`. Храните резервные копии **и базы пользователей, и ключа**, ограничьте права на оба файла. Ключ нельзя публиковать в Git или менять при перезапуске. Если существующие подключения есть, а ключ пропал, приложение не создаёт замену: требуется восстановить исходный ключ или удалить недоступные профили и добавить их заново. При смене переменной окружения нужно вернуть исходное значение ключа.

## Проверка

`python -m unittest discover -s tests -v` проверяет реальные временные SQLite-файлы, смену источника, чтение, блокирование записи, права/владение, перезапуск, шифрование, изоляцию избранного и контекст модели. Настройки PostgreSQL/MySQL, URL со специальными символами и блокировки опасных команд проверяются с подменой драйвера. Проверки с живыми PostgreSQL/MySQL требуют отдельных серверов и не входят в этот прогон.
