## Описание проекта

Приложение позволяет задавать вопросы к базе данных **на естественном языке** (русском или английском), а локальная языковая модель (Ollama) автоматически генерирует соответствующий SQL-запрос и выполняет его.

Учебная база построена по структуре **Гродненского государственного университета имени Янки Купалы**: все 13 факультетов, подтверждённые кафедры и военные учебные циклы, специальности и варианты подготовки из плана приёма 2026 года. Официальный справочник хранится в `grsu_catalog.json`, источники и границы достоверности описаны в [GRSU_DATA.md](GRSU_DATA.md).

Студенты, преподаватели, дисциплины, расписание, оценки и финансовые записи искусственные. Названия факультетов, кафедр, специальностей, деканы по официальному справочнику и адреса общежитий взяты из публичных источников. Учебные количества студентов и преподавателей не являются статистикой ГрГУ.

Ключевая особенность проекта — встроенная **многоуровневая система безопасности (Security-by-Design)**, реализующая четыре независимых рубежа защиты от SQL-инъекций (CWE-89), prompt injection и DoS-атак.

## Основные возможности

### Функциональные
- Генерация SQL-запросов из текста на русском и английском языках
- Проверенные SQL-шаблоны для вопросов из меню примеров; для остальных вопросов — генерация с примерами, внешними ключами и значениями справочников
- Выполнение запросов и отображение результатов в таблице
- Редактирование сгенерированного SQL перед выполнением
- Личная история запросов с индикацией заблокированных попыток
- Личное избранное — сохранение полезных запросов
- Серверный экспорт результатов в CSV и Excel для ролей с правом экспорта
- Вход, смена пароля, роли и управление пользователями
- Пробное выполнение изменяющих SQL-команд с откатом и отдельным подтверждением сохранения
- Журнал действий с фильтрами по логину, действию и датам
- Просмотр структуры и интерактивная SVG-диаграмма связей. Кэш схемы действует пять минут, кнопка «Обновить схему» перечитывает её сразу.
- Личные подключения администратора к SQLite, PostgreSQL и MySQL 8+ с проверкой доступа и шифрованием реквизитов; внешние базы доступны для чтения. См. [CONNECTIONS.md](CONNECTIONS.md)

### Безопасность
- 🔒 **Рубеж 1 — фильтрация вопроса**: блокировка попыток prompt injection и инъекций прямо в тексте вопроса до передачи в LLM
- 🔒 **Рубеж 2 — разбор SQL**: `sqlparse` определяет тип оператора и выделяет токены и вложенные конструкции; SQLite проверяет синтаксис при подготовке запроса. Разрешён один оператор, ограничены длина и вложенность. Проверки команд учитывают строковые литералы, поэтому текст `'UPDATE; DROP TABLE students'` внутри SELECT не становится командой изменения данных.
- 🔒 **Рубеж 3 — права и выполнение**: гостю и аналитику доступно только чтение; оператор и администратор могут изменять данные через пробный запуск и отдельное подтверждение. Чтение выполняется через SQLite `mode=ro` и `query_only`. Для всех ролей запрещены служебные операции (`ATTACH`, `PRAGMA`, управление транзакциями), прямой доступ к системным объектам, создание триггеров/представлений и функции вне разрешённого списка.
- 🔒 **Рубеж 4 — ограничения ресурсов и аудит**: таймаут SQL по умолчанию 3 секунды, выборка до 1000 строк, ограничение частоты запросов по IP и журнал значимых действий. Прерывание SQL откатывает незавершённую транзакцию.

## Установка и запуск

### 1. Клонировать репозиторий

```powershell
git clone https://github.com/Alshbetta/depKrim.git
cd depKrim
```

### 2. Подготовить окружение и зависимости

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

Команды ниже используют Python из виртуального окружения; активировать его отдельно не требуется.

### 3. Создать демонстрационную базу данных

```powershell
.\.venv\Scripts\python.exe database.py
```

Создаётся файл `grsu.db` рядом с `database.py`: 18 связанных таблиц, 13 факультетов, 49 кафедр и 3 военных учебных цикла, 59 записей специальностей/вариантов подготовки (56 разных кодов), 55 вымышленных преподавателей, 58 учебных дисциплин и 260 вымышленных студентов — по 20 на каждый факультет. Генератор также заполняет расписание, зачисления, оценки и 6 общежитий. Фиксированное начальное значение генератора случайных чисел делает набор воспроизводимым.

Повторный запуск не добавляет дубликаты и не меняет данные: если хотя бы одна таблица уже заполнена, заполнение пропускается. Частично заполненную базу генератор автоматически не восстанавливает. Для нового набора сначала сохраните существующий файл отдельно и уберите его из пути `grsu.db`. Единственная учебная база проекта — `grsu.db`; прежние демонстрационные базы и их резервные копии удалены из рабочей папки.

В учебном наборе фамилии и отчества согласованы с именами. Три преподавателя работают на двух кафедрах, по половине ставки на каждой, поэтому пример про совместительство возвращает три записи.

Для исправления ФИО и добавления совместительства в базе, созданной ранней версией генератора, выполните:

```powershell
.\.venv\Scripts\python.exe repair_demo_data.py
```

Скрипт работает с текущей `grsu.db`: сначала сохраняет резервную копию SQLite с префиксом `grsu-before-data-fix-` в `.local-backups/`, затем исправляет известные формы учебных ФИО и добавляет недостающие связи кафедр. Повторный запуск не добавляет дубликаты.

Специальности связаны с факультетами напрямую через `specializations.faculty_id`. Не подтверждённая источником выпускающая кафедра остаётся `NULL` в `department_id`; строить через это поле выборку всех студентов факультета нельзя. Экзаменационные отметки — от 1 до 10, зачёты имеют текстовый результат в `assessment_result`, а `score = NULL`. Группы согласованы с факультетом и специальностью; их обозначения учебные. Денежные значения синтетические, в BYN. В конфиденциальной таблице используются заведомо демонстрационные идентификаторы `DEMO-BY-…` вместо российских СНИЛС/ИНН.

### 6. Первый вход и пользователи

При первом запуске создаётся отдельная служебная база `app_users.db` и учётная запись `admin`. Случайный временный пароль записывается в `.initial-admin-password` рядом с `app.py`; путь также выводится в терминале. Откройте этот файл, войдите и задайте собственный пароль. До смены временного пароля доступ к данным и другим функциям API закрыт. После смены пароля файл удаляется.

Пароль должен содержать от 10 до 128 символов, строчную и заглавную буквы, цифру и специальный символ и не содержать логин. В служебной базе сохраняются хеши паролей, не исходные пароли.

Администратор открывает «Управление пользователями» в боковой панели: создаёт учётные записи с временными паролями, меняет роли и удаляет пользователей. Собственную запись удалить или понизить её роль нельзя. После изменения роли или удаления учётной записи старые сеансы перестают работать. Смена пароля завершает остальные сеансы пользователя.

| Роль | Возможности в этой версии |
|---|---|
| Гость | Вход в выданную учётную запись, чтение открытых таблиц, генерация SQL, личная история и избранное |
| Аналитик | Возможности гостя и экспорт CSV/Excel |
| Оператор | Возможности аналитика и изменение открытых данных/схемы через пробный запуск и подтверждение |
| Администратор | Доступ ко всем таблицам, изменения с подтверждением, экспорт, управление пользователями и аудит |

Сеанс действует восемь часов. Ключ подписи сессий сохраняется в `.session-key`, поэтому перезапуск приложения не сбрасывает вход. Файлы `app_users.db`, `.initial-admin-password` и `.session-key` исключены из Git. Для переноса локальной установки сохраняйте служебную базу и ключ вместе. При необходимости собственный ключ и первый временный пароль можно задать переменными окружения `SECRET_KEY` и `INITIAL_ADMIN_PASSWORD` до первого запуска.

### Пробный запуск и сохранение SQL

Для оператора и администратора разрешены `INSERT`, `UPDATE`, `DELETE`, `CREATE TABLE`, `CREATE INDEX`, `ALTER TABLE`, `DROP TABLE` и `DROP INDEX`. Служебные команды, виртуальные таблицы, триггеры и представления не входят в белый список. Оператор не может читать, менять или переименовывать таблицы `conf_`, в том числе через косвенные обращения.

1. Сгенерируйте SQL или отредактируйте запрос в карточке результата.
2. Нажмите «Проверить / выполнить». SELECT сразу возвращает данные; изменяющий оператор выполняется в SQLite-транзакции и откатывается.
3. Проверьте SQL и результат пробного запуска. Для сохранения нажмите отдельную кнопку «Сохранить изменения».

Подтверждение одноразовое и действует две минуты. Оно связано с пользователем, версией его сессии, точным SQL и состоянием базы. Если запрос отредактирован, права пользователя изменились или база обновилась после проверки, нужен новый пробный запуск. Генерация изменяющего SQL сама по себе данные не сохраняет. Ограничения внешних ключей включены при выполнении; ошибки и таймауты откатывают транзакцию.

Sandbox в этой версии означает транзакцию SQLite с откатом, а не отдельную виртуальную машину. Результаты чтения ограничены 1000 строками; время выполнения ограничивают progress handler и прерывание SQLite. Дополнительно ограничены размеры SQL и значений и набор доступных функций.

### Журнал и ограничения частоты

Кнопка «Журнал действий» доступна администратору. В `app_users.db` сохраняются входы (включая неудачные), выходы, смены пароля, генерация, пробный запуск и выполнение SQL, экспорт и управление пользователями. Запись содержит время, пользователя, IP соединения, тип действия, SQL/вопрос и результат. Пароли, ключи сессий, CSRF-токены и токены подтверждения не записываются. Старые события до внедрения журнала не восстанавливаются.

Фильтры: точный логин, действие и период дат включительно. Вывод разбит на страницы по 50 записей. Пробный запуск отмечен как «Откат», успешное сохранение — как «Сохранено».

По умолчанию для одного IP за 60 секунд разрешены 120 API-запросов суммарно, из них не более 10 попыток входа, 10 генераций, 30 выполнений SQL и 20 экспортов. При превышении возвращаются HTTP 429 и `Retry-After`. Клиентский `X-Forwarded-For` не используется. Счётчики хранятся в памяти процесса и сбрасываются при его перезапуске; для нескольких серверных процессов потребуется общее хранилище лимитов.

Параметры задаются в `app.config`: `SQL_TIMEOUT_SECONDS`, `SQL_PREVIEW_TTL`, `RATE_LIMIT_ENABLED` и `RATE_LIMITS`. Таблицы журнала и подтверждений создаются автоматически при запуске, без пересоздания пользователей.

### Локальные данные

`grsu.db`, `history.json` и `favorites.json` хранятся рядом с `app.py` и исключены из Git. База создаётся командой выше. При отсутствии файлов истории и избранного приложение возвращает пустые списки и создаёт файлы при первой записи. Учётные записи, пароли и журнал находятся в отдельной `app_users.db` и при смене учебного набора сохраняются.

Старые `shop.db`, `university.db` и их резервные копии удалены из рабочей папки. История и избранное сохраняются в исходных файлах. Записи без `user_id` не приписываются новым пользователям и не отображаются в их интерфейсе. Новые записи принадлежат вошедшему пользователю; читать и удалять их может только владелец. Администратор также видит только свою историю и избранное.

Локальные данные не нужно копировать из чужой рабочей папки. Перед удалением или пересозданием базы сохраните нужные данные отдельно. Каталог `.local-backups/` предназначен для локальных резервных копий и также исключён из Git. Уже существующие данные остаются на диске; прежние версии файлов сохраняются в истории репозитория.

## Как работать с приложением

1. Войдите и при необходимости смените временный пароль. Перейдите во вкладку **«Структура»** — просмотрите доступные таблицы и их поля.
2. Введите вопрос на русском или английском, например:
   - `Покажи всех студентов факультета математики и информатики`
   - `Покажи студентов специальности Кибербезопасность`
   - `Сколько студентов проживает в каждом общежитии?`
   - `Show students from the Faculty of Mathematics and Informatics`
3. Нажмите **«Сгенерировать SQL»**.
4. Проверьте сгенерированный запрос и нажмите **«Выполнить»**.
5. Сохраняйте полезные запросы в **«Избранное»** кнопкой ★.
6. Экспортируйте результаты в **CSV**, **Excel** или **PDF**. PDF включает исходный вопрос, выполненный SQL и таблицу с нумерацией строк. Для кириллицы используется системный шрифт Arial, DejaVu Sans или Liberation Sans.

> **Примечание:** Запросы, содержащие попытки инъекций или опасные конструкции, блокируются автоматически. В интерфейсе отображается причина блокировки.

## Примеры заблокированных запросов

Система автоматически блокирует следующие типы угроз:

покажи всех пользователей' OR '1'='1     → Рубеж 1: тавтологическая инъекция
DROP TABLE students                     → Гость/аналитик: запрет изменения данных
SELECT * FROM students WHERE 1=1         → Рубеж 2: тавтология WHERE
SELECT * FROM sqlite_master              → Рубеж 2: разведка структуры БД
SELECT id FROM students UNION SELECT id FROM professors → Рубеж 2: UNION-атака
SELECT SLEEP(5)                          → Рубеж 2: DoS-атака

## Проверка университетской базы

### Как проверяется генерация

В `prompts.json` хранятся проверенные пары «вопрос — SQL». При совпадении вопроса (без учёта регистра, лишних пробелов и знаков препинания) приложение использует соответствующий шаблон и проверяет его на текущей базе. Это обеспечивает стабильные ответы на вопросы из меню примеров без обращения к Ollama.

Для других вопросов модель получает связи `FOREIGN KEY`, значения публичных справочников и до трёх похожих примеров. SQL проходит фильтры безопасности и компиляцию через `EXPLAIN` в соединении только для чтения. При ошибке таблицы, колонки или синтаксиса модель получает сообщение SQLite и одну попытку исправления. Непрошедший проверку SQL не выполняется. Проверка компиляции не гарантирует правильность смысла произвольного запроса или его результата.

### Автоматические проверки

```powershell
.\.venv\Scripts\python.exe -m unittest discover -s tests -v
```

Проверки используют временные базы и подменяют обращение к Ollama. Проверяются учебные данные, генерация SQL, авторизация, роли, CSRF, изоляция пользовательских данных, запрет доступа к `conf_`, откат DML/DDL, подтверждения и их срок действия, таймауты с частично выполненными изменениями, внешние ключи, лимиты по IP, аудит и его фильтры. Локальные базы, история и избранное не меняются.
